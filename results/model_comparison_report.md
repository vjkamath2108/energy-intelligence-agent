# LLM Inference for Energy Operations — Model Comparison Report

**Date:** 2026-06-22  
**Author:** Vijay Kamath  
**Project:** Energy Intelligence Agent (EIA)  
**System:** Apple M4 Max (16-core CPU, 40-core GPU, 128 GB unified memory)

This report consolidates benchmark results from two evaluation runs conducted
across six weeks of development. It covers both the Stream 1 anomaly explanation
pipeline and the EIA RAG dispatch pipeline, and is intended as a reference for
teams choosing between managed frontier inference, open-weight managed inference,
and sovereign self-hosted inference for energy operations workloads.

---

## The Core Question

Can you match frontier-model quality on structured energy operations tasks
using open-weight models that keep data entirely within your own network?

For NIS2-regulated UK energy operators, this is not academic — an external
API endpoint is a supply chain dependency that may not be acceptable under
their security risk model. The benchmark answers the question with real numbers.

## Dataset & Methodology

**Dataset:** 300 synthetic EKS log events (seed=42, fully reproducible).
Generated by `stream1_log_anomaly/src/streaming/generate_logs.py`.

**Anomaly detector:** Isolation Forest (contamination=auto). All six models
received exactly the same 49 flagged events and the same ±5 context window.

**Ground truth (Option B):** Severity accuracy is measured only on events
within injected anomaly windows. The 20 isolated false-positive events from
the Isolation Forest are excluded from accuracy scoring — ground truth for
those is ambiguous by design.

**Three injected anomaly patterns:**

| Pattern | Events | Failure mode | Ground truth |
|---|---|---|---|
| A — Cascade | 60–69 | auth → inventory → payment-svc → api-gateway; all ERROR 500, 1.5–2.5s latency | HIGH |
| B — Latency spike | 130–139 | payment-svc sustained high latency (2–4s), mixed 200/500 | HIGH |
| C — Error surge | 200–212 | api-gateway elevated 500s, normal latency (100–400ms) | HIGH |

Pattern C is the hardest: HIGH severity must be inferred from error rate alone,
with no latency signal. It reliably separates models that understand the
operational context from those that rely on the latency heuristic.

**Quantisation:** All Ollama models served in GGUF format. Default Ollama pulls
use Q4\_K\_M quantisation unless otherwise noted. The primary quality loss from
Q4→Q5 on 7B models is approximately 1–3% perplexity increase; on 3B models the
impact is larger because the parameter budget is already constrained.

### Pattern C Detail — Error Surge Without Latency

This is the benchmark's most diagnostic test. Models that simply associate
HIGH severity with high latency will fail it. Pattern C demands understanding
that repeated 500 errors across a service are operationally significant even
when response times look normal.

| Model | Pattern C accuracy |
|---|---|
| Claude Sonnet 4.5 (Bedrock) | 9/12 (75%) |
| Mistral 7B (Bedrock) | 12/12 (100%) |
| Mistral 7B (Sovereign) | 12/12 (100%) |
| phi4-mini (Ollama) | 12/12 (100%) |
| llama3.2:3b (Ollama) | 1/12 (8%) |
| qwen3:14b (Ollama) | 3/12 (25%)† |

Both Mistral 7B variants and phi4-mini achieve perfect Pattern C accuracy.
Claude Sonnet misses 3/12 Pattern C events — the narrative explanations are
high quality but it occasionally classifies sustained 500 bursts without
latency spikes as MEDIUM rather than HIGH.

## EIA RAG Pipeline Results

The RAG dispatch pipeline adds a retrieval layer (BM25 + pgvector + RRF)
before inference. Results here cover retrieval quality and recommendation
safety — the LLM backend is swappable (Bedrock or Ollama) via a single flag.

### Retrieval Quality

| Retrieval configuration | Precision@5 |
|---|---|
| BM25 only (PostgreSQL tsvector) | 0.58 |
| Semantic only (pgvector cosine) | 0.64 |
| Hybrid BM25 + semantic + RRF fusion | **0.78** |

The hybrid retriever closes a 0.20 gap over BM25-only. RRF fusion is the
decisive factor — it re-ranks results from both retrievers without requiring
a learned combination weight, which keeps the system maintainable as the
document corpus grows.

### Recommendation Safety Layer

The safety layer runs on every recommendation, regardless of which LLM
backend produced it. Two checks run sequentially:

1. **Term overlap** (always): fraction of meaningful tokens in the
   recommended action that appear verbatim in the retrieved context.
   Gate: ≥ 30%. Operates without any model calls — pure text comparison.

2. **Semantic similarity** (optional): cosine distance between embedded
   claim and embedded corpus. Gate: ≥ 0.50. Requires an embedder
   (Bedrock Titan V2 or equivalent). Skipped in sovereign/test mode.

The CI eval gate (`evaluation/ci_gate.py`) verifies the safety layer using
5 golden (query, context, response) tuples. Term overlap across 5 grounded
scenarios: 57–79%. A deliberately ungrounded response ("portfolio strategy
optimisation…" against a Capacity Market penalty document) achieves 4%
overlap — correctly flagged.

### Confidence Calibration

| Scenario | Confidence | Human review? |
|---|---|---|
| BSUoS charge (grounded) | 0.867 | No |
| TNUoS tariff (grounded) | 0.802 | No |
| BM dispatch (grounded) | 0.822 | No |
| Grid Code ECC.6.3.2 (grounded) | 0.824 | No |
| Hallucination case (ungrounded) | 0.262 | **Yes** |

Confidence drops from 0.80–0.87 on grounded responses to 0.26 on the
ungrounded case. The composite scorer (60% LLM self-reported confidence,
25% safety result, 15% citation coverage) separates the two bands cleanly.
Brier score on the validation set: 0.14 (gate < 0.20).

### Full Pipeline Latency (Demo Mode, No LLM)

| Percentile | Latency |
|---|---|
| P50 | ~10ms |
| P95 | ~80ms |

These figures cover the orchestration layer only (retrieval, safety, audit,
RAG log). Production latency adds the LLM inference time from the tables above.
A Bedrock dispatch at P95 costs approximately 6,755ms (explanation) +
80ms (orchestration) + ~50ms (retrieval) ≈ **7s end-to-end**.
A phi4-mini sovereign dispatch costs approximately 2,330ms + 80ms + 50ms
≈ **2.5s end-to-end** with zero external calls.

## Quantisation Trade-offs (Q4 / Q5 GGUF)

All Ollama models in this benchmark used Q4\_K\_M quantisation (the Ollama
default for most model pulls). The relevant trade-offs for production sovereign
deployments:

| Quantisation | Size (7B model) | Quality vs FP16 | Throughput vs FP16 |
|---|---|---|---|
| FP16 (full precision) | ~14 GB | Baseline | Baseline |
| Q5\_K\_M | ~5.5 GB | −1–2% perplexity | +20–30% |
| Q4\_K\_M | ~4.4 GB | −3–5% perplexity | +40–60% |
| Q3\_K\_M | ~3.6 GB | −8–12% perplexity | +70–90% |

**Practical findings from this benchmark:**

- **Q4\_K\_M is sufficient for Mistral 7B on this task.** Mistral 7B at Q4\_K\_M
  achieved 100% severity accuracy and 100% JSON validity. The quantisation loss
  did not manifest as accuracy degradation on structured extraction tasks.

- **Q4\_K\_M on 3B models is too aggressive.** llama3.2:3b at Q4\_K\_M achieved
  only 7% severity accuracy. The 3B parameter budget is already at the floor for
  complex structured reasoning; Q4 quantisation compounds the loss.

- **qwen3:14b's failure mode is not quantisation.** Its 51% JSON validity comes
  from extended chain-of-thought mode exhausting the 512-token prediction budget
  before completing JSON output. Increasing `num_predict` to 1024 reduces but
  does not eliminate failures. The fix is to disable thinking mode explicitly
  (`/set parameter thinking false` in Ollama) or use a dedicated instruction
  variant. This is an inference configuration issue, not a model quality issue —
  qwen3:14b at full capability likely performs well.

**Recommendation:** Use Q4\_K\_M for 7B+ sovereign deployments — the accuracy
cost is negligible on structured extraction tasks. For 3B models, use Q5\_K\_M
or accept accuracy loss. Avoid 3B models for production severity classification.

| Dimension | Claude Sonnet (Bedrock) | Mistral 7B (Bedrock) | Mistral 7B (Sovereign) | phi4-mini (Ollama) |

| Data residency | AWS region | AWS region | Client VPC | Client machine |
| NIS2 compliant | Requires DPA review | Requires DPA review | **Yes — zero egress** | **Yes — zero egress** |
| Severity accuracy | 83% | 100% | 100% | 97% |
| P95 latency | 6,755ms | 1,812ms | 3,566ms | 2,330ms |
| Hardware needed | AWS managed | AWS managed | ≥32 GB RAM or GPU | ≥8 GB RAM |

| Ops burden | Low | Low | Medium | Low |
| Production-ready | Yes | Yes | With GPU | Yes (dev/staging) |

### Cost Crossover

At current Bedrock pricing, the crossover from Claude Sonnet to self-hosted
infrastructure occurs at approximately **50M tokens/day** (based on g5.xlarge
on EKS at ~$1.00/hr vs ~$0.003/call). Mistral 7B via Bedrock crosses to
self-hosted at a much higher volume (~500M tokens/day) due to lower API cost.
For most UK energy operators, volume is well below these thresholds — the
decision is driven by data residency, not cost.

## Recommendations by Use Case

### Development and Testing
**Use phi4-mini via Ollama.**  
97% accuracy, P95 2.3s, zero cost, zero external dependency. The sole
trade-off is 9/10 Pattern A cascade accuracy vs 10/10 for Mistral 7B.
For development iteration this is acceptable. phi4-mini runs comfortably
on a MacBook with 16 GB RAM (4.4 GB Q4\_K\_M GGUF).

### Production — Cloud-First Client
**Use Mistral 7B via Bedrock.**  
100% accuracy, P95 1.8s, ~$0.0001/call. Outperforms Claude Sonnet on this
structured task at 30× lower cost. Claude Sonnet's advantage is on
open-ended reasoning, summarisation, and multi-step tasks — not constrained
structured JSON extraction. For anomaly explanation and dispatch recommendation,
the smaller model wins.

### Production — NIS2-Regulated Client (Critical Infrastructure)
**Use Mistral 7B via Ollama → production EKS (vLLM) within client VPC.**  
Match quality to Bedrock deployment (100% accuracy) with zero external
data egress. Recommended hardware: g5.xlarge (A10G, 24 GB VRAM) on EKS
running vLLM. Expected latency on GPU hardware: P50 ~800ms, P95 ~1.2s.
Local developer testing uses Ollama on M4 Max as a drop-in replacement
for the same model.

### High-Volume Production (> 50M tokens/day)
**Self-hosted EKS from day one, regardless of sovereignty requirements.**
At this volume, Bedrock costs exceed EKS infrastructure costs. Mistral 7B
on vLLM at g5.xlarge achieves ~800ms P50 latency at substantially lower TCO.

## What Went Wrong — Honest Assessment

### 1. qwen3:14b results are unreliable
The benchmark included qwen3:14b as a candidate for high-quality sovereign
inference. Results (41% accuracy, 51% JSON validity) are partially invalid
due to token budget exhaustion from chain-of-thought mode. The fix is known:
disable thinking mode. I did not re-run the full benchmark with thinking
disabled due to time constraints. The reported figures understate qwen3:14b's
capability.

**Impact:** The benchmark can be re-run in under 2 hours with
`OLLAMA_NUM_PREDICT=2048` and `thinking: false` in the Ollama options.
qwen3:14b at 14B parameters is the most likely candidate to exceed Mistral 7B
accuracy on the error-surge pattern once properly configured.

### 2. Human quality ratings not included
Severity accuracy measures correctness of a categorical label. It does not
measure whether the explanation is *useful* to an on-call engineer. A correct
HIGH label attached to a generic "resource exhaustion" explanation has less
operational value than a specific "auth-service OAuth token validation latency
spike caused by downstream Redis timeout" explanation.

**Impact:** Real production evaluation needs on-call engineer ratings (1–5
scale) on a sample of explanations. This was planned but not executed. The
severity accuracy numbers should be treated as a floor, not a ceiling.

### 3. RAG pipeline not benchmarked end-to-end with real retrieval
The EIA RAG quality numbers (Precision@5, Brier score) were measured on
components in isolation. A full end-to-end benchmark — real queries against
a PostgreSQL database with a populated document corpus — would reveal
retrieval–generation interaction effects not captured by component-level eval.

**Impact:** The retrieval Precision@5 of 0.78 is representative but was
measured on a small golden eval set (15 queries). A larger evaluation set
would tighten the confidence interval.

### 4. No latency breakdown across pipeline stages
Production end-to-end latency is the sum of retrieval, LLM inference, safety
check, audit write, and RAG log write. Individual stage latencies were not
instrumented separately in the benchmark. The Langfuse traces (when running
with real credentials) would surface this breakdown automatically.
