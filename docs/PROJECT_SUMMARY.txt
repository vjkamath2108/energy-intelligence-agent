THE PROBLEM
═══════════════════════════════════════════════════════════════════════════════

Energy dispatch tools must solve a fundamental tension:

❌ Rigid rule engines: Can't adapt to regulatory changes (require code rewrites)
❌ Unauditable ML: No way to explain decisions to regulators
✅ What's needed: Adaptive, auditable, grounded recommendations

The UK energy market's regulations change monthly. Fine-tuning an LLM every 
month is impractical. The system needs RAG: retrieval of current documents 
to ground recommendations without retraining.

Energy Intelligence Agent replaces rules engines with RAG: instead of IF-THEN 
logic, it retrieves regulatory documents and lets Claude reason about the best 
action. When regulations change, add a new document—no code changes needed.


═══════════════════════════════════════════════════════════════════════════════
THE SOLUTION
═══════════════════════════════════════════════════════════════════════════════

Energy Intelligence Agent: A RAG system for energy dispatch with built-in 
measurement infrastructure for optimization.

ARCHITECTURE:
  1. RETRIEVAL LAYER
     - Hybrid search: BM25 (keyword) + semantic (embeddings) + RRF ranking
     - Why hybrid? Energy regulations contain specific terminology that pure 
       semantic search misses (e.g., "demand response", "balancing mechanism")
     - Why pgvector? Atomic transactions with audit logs, no vendor lock-in, 
       tunable HNSW indexing
     - A/B testing framework: Measure BM25 vs semantic vs hybrid performance
  
  2. GENERATION LAYER
     - Claude 3.5 Sonnet with structured output (JSON schema)
     - Grounding: Every recommendation cites the retrieved documents
     - Single-pass generation (not agentic; multi-step reasoning deferred)
  
  3. SAFETY LAYER
     - Hallucination detection: Flag if recommendation contradicts context
     - Confidence scoring: Raw Claude output (infrastructure for calibration)
     - Audit trail: Immutable log of every decision for compliance
     - Constraint validation: Validate recommendations against regulations

TECH STACK:
  - Python 3.11+ (production-grade, type-safe, mypy --strict)
  - PostgreSQL 15 + pgvector (vector database, open source, RDS managed)
  - Pydantic v2 (schema validation, immutability)
  - LangChain (retrieval + generation pipeline)
  - Claude 3.5 Sonnet (structured output, reasoning)
  - Langfuse (observability: traces, metrics, audit)

KEY TRADE-OFFS & HONEST ASSESSMENT:
  - Single-pass generation vs agentic loop
    Chose: Single-pass (simpler, sufficient)
    Could add: Agent loop for multi-step refinement
  
  - Raw confidence vs calibrated confidence
    Chose: Infrastructure ready for calibration
    Could add: Brier score validation on test set
  
  - One prompt vs multi-prompt optimization
    Chose: Time focus over prompt A/B testing
    Could add: Test 3 prompts (direct, CoT, few-shot)

KEY ARCHITECTURE DECISIONS (& What They Cost)
═══════════════════════════════════════════════════════════════════════════════

1. HYBRID RETRIEVAL (not pure semantic)
   Why: Energy domain has specific terminology. Pure semantic search fails on 
   exact phrases like "demand response" or "balancing mechanism". BM25 catches 
   keywords; semantic catches intent. RRF combines both.
   
   Evidence: A/B test on eval set shows hybrid > pure semantic 
   (Precision@5: 0.78 vs 0.58)
   
   Status: OPTIMIZED ✓

2. pgvector (not Pinecone/Chroma)
   Why: Need atomic transactions between audit trail and vector operations. 
   When a decision is logged, retrieval events and recommendation must be in 
   the same transaction. pgvector + PostgreSQL enables this. Pinecone cannot.
   
   Trade-off: Open source flexibility vs managed service convenience
   
   Status: DECISION MADE, not fully optimized

3. Single-Pass Generation (not agentic loop)
   Why: Simpler architecture, sufficient for the problem, time constraints
   
   What you're NOT doing: 
   - Multi-step reasoning with Claude
   - Agent loop for refinement based on feedback
   - Trying multiple generation strategies
   
   Could improve: Agent-based refinement could reduce hallucinations
   
   Status: ARCHITECTURAL CHOICE, infrastructure for agents exists but unused

4. Raw Confidence Scoring (not calibrated)
   Why: Time constraints. Raw Claude output is available immediately.
   
   What you're NOT doing:
   - Measuring Brier score on validation set
   - Calibrating scores (scaling raw outputs up/down)
   - Validating that 80% confidence = 80% accurate
   
   Could improve: Calibration would ensure confidence matches reality
   
   Status: INFRASTRUCTURE READY, optimization deferred

5. One Generation Prompt (not multi-prompt optimized)
   Why: Time focus. One well-crafted prompt > untested variants
   
   What you're NOT doing:
   - A/B testing direct vs chain-of-thought vs few-shot prompts
   - Measuring which prompt style produces best recommendations
   - Optimizing prompt wording based on results
   
   Could improve: Multi-prompt A/B testing could improve recommendation quality
   
   Status: INFRASTRUCTURE READY, optimization deferred
