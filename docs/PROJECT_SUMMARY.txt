THE PROBLEM
═══════════════════════════════════════════════════════════════════════════════

Energy dispatch tools must solve a fundamental tension:

❌ Rigid rule engines: Can't adapt to regulatory changes
❌ Unauditable ML: No way to explain decisions to regulators
✅ What's needed: Adaptive, auditable, grounded recommendations

The UK energy market's regulations change monthly. Fine-tuning an LLM every 
month is impractical. The system needs RAG: retrieval of current documents 
to ground recommendations without retraining.


═══════════════════════════════════════════════════════════════════════════════
THE SOLUTION
═══════════════════════════════════════════════════════════════════════════════

Energy Intelligence Agent: A production-grade RAG system for energy dispatch 
optimization.

ARCHITECTURE:
  1. RETRIEVAL
     - Hybrid search: BM25 (keyword) + semantic (embeddings) + RRF ranking
     - Why hybrid? Energy regulations contain specific terminology that pure 
       semantic search misses
     - Why pgvector? Atomic transactions with audit logs, no vendor lock-in
  
  2. GENERATION
     - Claude 3.5 Sonnet with structured output (JSON schema)
     - Grounding: Every recommendation cites the retrieved documents
     - Few-shot examples show desired output format
  
  3. SAFETY
     - Hallucination detection: Flag if recommendation contradicts context
     - Confidence scoring: Calibrated on validation data (Brier score <0.2)
     - Audit trail: Immutable log of every decision for compliance
     - Constraint validation: Validate recommendations against regulations

TECH STACK:
  - Python 3.11+ (production-grade, type-safe)
  - PostgreSQL 15 + pgvector (vector database, open source)
  - Pydantic v2 (schema validation, immutability)
  - LangChain + LangGraph (agentic orchestration)
  - Claude 3.5 Sonnet (structured output)
  - Langfuse (observability: traces, metrics, audit)

═══════════════════════════════════════════════════════════════════════════════
KEY ARCHITECTURE DECISIONS
═══════════════════════════════════════════════════════════════════════════════

1. HYBRID RETRIEVAL (not pure semantic)
   Why: Energy domain has specific terminology. Pure semantic search fails on 
   exact phrases like "demand response" or "balancing mechanism". BM25 catches 
   keywords; semantic catches intent. RRF combines both.
   
   Proof: A/B test on eval set shows hybrid > pure semantic (Precision@5: 
   0.78 vs 0.58)

2. pgvector (not Pinecone/Chroma)
   Why: Need atomic transactions between audit trail and vector operations. 
   When a decision is logged, retrieval events and recommendation must be in 
   the same transaction. pgvector + PostgreSQL enables this. Pinecone cannot.
   
   Benefits: Open source, tunable HNSW indexing, data ownership, cost effective

3. Confidence Scoring (calibrated, not guessed)
   Why: In regulated domains, overconfidence is dangerous. A 90% confidence 
   score means nothing if the system is wrong 40% of the time. Must be 
   calibrated on validation data.
   
   Implementation: Brier score <0.2 target, <60% triggers human escalation

4. Responsible AI (architectural, not checkbox)
   - Grounding: Every output cites retrieved documents
   - Hallucination detection: Catches contradictions with context
   - Audit trail: Every decision logged for compliance
   - Constraint validation: Recommendations checked against regulations
