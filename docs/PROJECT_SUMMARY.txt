PROJECT SCOPE:

  Energy dispatch optimization system for UK energy markets.
  
  Input: "How should we handle peak demand at 6PM given current regulations?"
  
  System:
    1. Retrieves relevant documents (regulations, customer data, historical decisions)
    2. Uses Claude to generate a dispatch recommendation grounded in those docs
    3. Detects hallucinations (does recommendation contradict context?)
    4. Scores confidence (0–100) calibrated on validation data
    5. Logs full audit trail (every decision is traced and auditable)
  
  Output: DispatchRecommendation with:
    - Action: specific dispatch instruction
    - Reasoning: grounded in retrieved context
    - Confidence score: calibrated + human review if <60%
    - Audit trace: full path from query → retrieval → generation → decision


TECH STACK (production-ready):
  Language: Python 3.11+ (idiomatic, type-hinted, async)
  Vector DB: pgvector + PostgreSQL (open-source, no vendor lock-in)
  Retrieval: BM25 (keyword) + semantic (embeddings) with Reciprocal Rank Fusion
  LLM: Claude 3.5 Sonnet (structured output, strong reasoning)
  Data validation: Pydantic v2 (type-safe schemas)
  Orchestration: LangChain/LangGraph (agentic system design)
  Observability: Langfuse (traces, metrics, debugging)
  Testing: pytest + mypy + ruff (quality gates)

After this project, you walk into Anthropic and say:

"I built Energy Intelligence Agent to understand production-grade RAG systems.

Here's the problem it solves: Energy dispatch is safety-critical. Wrong recommendations
cost customers money and violate regulations. Existing systems are either rigid rule
engines or black-box ML models. I wanted to build something grounded, auditable, and safe.

Architecture decisions:

1. RAG over fine-tuning:
   Regulations change monthly. RAG lets us update context without retraining.
   Fine-tuning would lock us into a frozen model. The ability to adapt to new
   regulations is the whole point.

2. pgvector over managed services:
   I evaluated Pinecone, Chroma, Weaviate. pgvector + PostgreSQL wins for me because:
   - Open-source (no vendor lock-in)
   - I can tune the indexing strategy myself
   - Atomic transactions with the rest of the database (important for audit)
   - I wanted to understand the trade-offs rather than abstract them away

3. Hybrid retrieval (BM25 + semantic):
   Pure semantic search misses domain terminology. Energy regulations talk about
   'peak demand response' and 'balancing mechanism' — these phrases don't embed
   well in isolation. BM25 catches exact phrases. I proved hybrid wins with A/B tests.

4. Confidence scoring:
   Every recommendation includes a confidence score. I calibrated it on a validation
   set so the score predicts accuracy. Below 60%, the system escalates to human review.
   This is how you build trust.

5. Audit trail:
   Every decision is logged with full context. An auditor can trace exactly why
   a recommendation was made. This matters in regulated domains.

Responsible AI is baked into the design, not added as an afterthought. Hallucination
detection is a component in the system, not a separate check. The audit trail isn't
optional logging — it's part of the pipeline.

For Python, this was my exercise in production-grade code. Every function has type
hints, I use async/await for I/O, error handling is explicit, test coverage is 80%+.
The code reflects the standards I expect at Anthropic.

Most interesting learning: Choosing the right retrieval strategy isn't obvious.
I evaluated 3 chunking approaches, 2 search methods, and combinations. The evaluation
framework I built lets me say: 'Here's the data proving hybrid is better.' That's the
difference between opinion and evidence.

If you hire me, you're getting someone who understands the full stack — from chunking
to orchestration — and has made defensible architectural decisions for a system that
actually has to work in production."
